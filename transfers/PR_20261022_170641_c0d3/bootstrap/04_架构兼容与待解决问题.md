# 架构兼容与待解决问题

## 结论

推荐状态为 `CONTINUE_WITH_TARGETED_REWORK`。当前候选保留了正确的 policy、窗口数学、canonical Full 与 Draft read 分离、方法接入和 owner 基础；没有证据支持从固定 base 全量重写。它也不能直接进入正式验收：固定配套 MRV2 明确要求 async-first，而 Eagle/GQA/DFlash 等路径的当前 exact 长度仍引入本特性新增 D2H/CPU consumer 屏障。此项是已确认的架构阻塞，不可仅交给性能测量裁决。

证据分类：

- `SOURCE_CONFIRMED`：在固定双仓源码中直接核实。
- `EXECUTABLE_EVIDENCE`：绑定当前候选 tree 的 Host/恢复/发布检查。
- `REPORT_ONLY`：旧版本、旧机器或尚未独立复核的报告。
- `INFERENCE`：根据已确认事实推导，仍需运行验证。
- `UNKNOWN`：现有材料不能判断。

## 1. Runner / speculator 生命周期

`SOURCE_CONFIRMED`：固定 vLLM 的 `docs/design/model_runner_v2.md` 明确将持久请求状态与 per-step 输入分离，并要求执行链 async-first，CPU entrypoint 只排队设备工作，避免显式与隐式同步。当前 Ascend 候选没有替换整个 model runner；Window 通过 speculator、metadata factory/callback 和 provider 接入。`draft_window_runtime.py::metadata_callback` 从当前 Full owner 和请求映射构建 Draft read，方法入口位于 Eagle3、DFlash、DSpark speculator。

`SOURCE_CONFIRMED`：factory 的 module interception 在固定 base 已存在；本特性增加 callback 作用域。最终候选为 callback 冲突、LIFO 和异常恢复补了合同检查，但其线程模型仍是假定单 worker 串行/LIFO。

`EXECUTABLE_EVIDENCE`：当前 tree 的 selector/factory/owner Host 合同与完整 `bash format.sh ci` 已通过；这些证据不证明设备 reader 完成或 engine overlap。

结论：接入点可以继续使用，但 exact-length consumer 和设备完成边界需定点重做；不需要重写 runner。

## 2. Full 写入与 Draft 读取边界

`SOURCE_CONFIRMED`：Window view 从 canonical Full block table 生成 fresh read backing；positions、slot mapping、Full query/context writes 和 Target metadata 仍由基线对象承担。`draft_window_plan.py` 保存 `H/E/S/V` 语义，provider 按 gid/layout 投影。

`EXECUTABLE_EVIDENCE`：Host alias、rejection、GQA write oracle 和数学边界测试覆盖了部分合同。它们不证明 fused MLA/Target writes、未捕获页或真实 native 读集。

`UNKNOWN`：所有 required backend、所有 gid 和真实通信后的 reader 是否都持有正确 backing，需模型与设备证据。

## 3. OFF / forced-OFF 与 selector

`SOURCE_CONFIRMED`：`spec_decode/__init__.py` 和 `draft_window_policy.py` 在 factory 创建前解析配置；CONFIG_OFF 不建立 Window feature state。MTP 与已识别的 dedicated V4/V4.1 DSpark route forced-OFF，投机方法本身保留。不支持的 Window ON 组合明确拒绝，没有静默 fallback。

`EXECUTABLE_EVIDENCE`：最终 tree 的 selector/factory Host 测试通过。

`UNKNOWN`：共训 DeepSeek-V4 DSpark 的真实 target/draft checkpoint 与 config 身份没有绑定，不能从路径前缀判定。实际 MTP/V4 engine OFF 回归未执行。

## 4. exact、upper 与同步（最高优先级）

`SOURCE_CONFIRMED`：Window 规划必须使用 preparation/rejection 后的当前 exact。反例 `E=1151, U=1152, W=1024, B=128` 中正确 `S=0`，若用 upper 得 `S=128`，会少读 128 个合法 token。

`SOURCE_CONFIRMED`：DSpark no-DCP ordinary MLA 分支可把同一次 preparation 已完成的 CPU/device exact pair 显式交给 runtime；候选已移除 Window 重复 `.to(cpu)`，保留基线 copy。其他 Eagle/GQA/DFlash 路径一般仍在 metadata build 获取 CPU exact；Eagle K-step 可每 step 一次。GQA/MLA 的 planner、list/chunk、native 参数等 CPU consumer 使“只把 projection 搬到设备”不足以消除同步。

`EXECUTABLE_EVIDENCE`：Host 反例证明 MLA 子路径 Window copy 计数从 1 降到 0 且基线 copy 仍为 1；这不是 NPU 时延或 overlap 证明。

`INFERENCE`：优先复用已有 device-length 路径（例如部分 SFA/indexer）并引入清晰的 device exact / host capacity descriptor，可能是最小方案；必须先在固定 torch_npu/CANN/native ABI 上核实 schema 与实际 consumer。

状态：`ARCHITECTURE_BLOCKED`。首个服务器问题即围绕这一契约，但必须先做 ABI/trace 事实收集，不能直接假设某最新网页接口存在。

## 5. 分配与生命周期

`SOURCE_CONFIRMED`：read materialization 为每 gid/build 分配或取得 owner 管理的 read backing；owner 在 native preparation 前建立，未知 completion 会 quarantine，容量压力才等待 completion。当前实现不通过 clone canonical 写侧来规避 alias。

`EXECUTABLE_EVIDENCE`：Host 覆盖 event 创建/record/bookkeeping/query/wait 失败、reverse completion、压力和 owner 状态机。

`UNKNOWN`：真实 engine 在部分 native submit 后 Host 异常、late HCCL/通信 reader、跨流依赖和最后 reader join 尚未证明。引用计数或当前流 event 不是跨流 completion 证明。

## 6. 方法差异

- Eagle3：`SOURCE_CONFIRMED`。首轮使用私有 Draft metadata；Window ON 跳过会覆盖 read view 的 Full updater。候选已修复 replicated PCP 首轮 step-0 metadata 双构建，并保留 Full gather/slots。全 AR steps、实际 rejection、PCP 通信和 Full/Target 数值为设备缺口。
- DFlash：`SOURCE_CONFIRMED`。实际 query width 由 runtime/preparation 决定，历史 K8 路线常见 Q=K+1；不能硬编码模型标签。
- DSpark：`SOURCE_CONFIRMED`。anchor 可形成 K 或 K+1；共享 DSA sparse index capacity 的 `+1` 修复有真实边界原因，并加显式 width guard。lazy buffer 有 lane×step 内存动机，仍需 warmup/profile/MRV1/Graph regression。

## 7. 并行、backend 与 Graph 边界

`SOURCE_CONFIRMED`：fixed base/candidate 对 MRV2 + legacy `enable_dsa_cp` 有启动 guard；候选撤回了无必要的 legacy `dsa_cp.py` Window 扩展，provider 明确拒绝。PCP 与 legacy DSA-CP 语义不同。

`REPORT_ONLY`：历史 GLM DSpark TP16/DP1/EP/Async 性能与设备报告绑定旧源码/overlay，不能成为当前 SHA PASS。

`UNKNOWN`：真实 FlashComm/SP collective 形状、通信后 backing reader、multi-gid provider、compressed DSA/SFA/indexer、GLM/Qwen required checkpoints 尚未闭环。

Draft Window Graph 不在本 PR；共享 `dsa_v1.py`、Triton indices、factory 等修改仍需 MRV1、Window OFF、warmup/profile 和已有 Graph capture/replay 代表回归。

## 8. 已确认修复与仍待解决

已在 `2604675…` 中确认的局部修复：

1. DSpark K/K+1 index capacity 显式校验与 `+1` 容量边界。
2. Eagle3 replicated PCP step-0 metadata 重复构建修复。
3. DSpark/no-DCP/ordinary MLA 当前 exact pair 复用，移除 Window 重复 copy。
4. 撤回不可达 legacy DSA-CP 共享实现，保留 guard 与 required gap。
5. factory callback 冲突、LIFO、异常恢复和 owner Host 合同补充。

仍是源码/架构问题：

1. A01：非上述 MLA 子路径的新增 exact D2H 与 CPU consumer 契约。
2. legacy DSA-CP 产品路线没有 provider/实现。
3. 部分 backend/multi-gid/非标准 residency provider 缺失。

仍是设备证据风险：

1. engine partial-submit、late reader、跨通信流 completion 与自然压力复用。
2. Eagle3 全 step/PCP、DFlash/DSpark native numerical、Full-write/Target 隔离。
3. FlashComm/SP、TP16/EP、prefix/chunked/mixed 生命周期。
4. 所有正式性能。

## 9. 官方风格与后续提交边界

- 继续复用 speculator、metadata builder、factory/callback 和 provider seam；不要复制整个 propose/metadata assembly。
- 配置行为要明确 OFF/forced-OFF/unsupported；不根据 model path 猜 route。
- 每次共享 backend 改动列出 Window OFF、MRV1、warmup/profile、Graph 调用者和回归。
- 每次新增同步/分配说明实际频次、owner、并发假设、释放和验证。
- 生产修改形成新 SHA/tree 后，旧设备/Host/性能结果按影响范围失效并重新绑定。
- 服务器不能在冻结 tree 热补丁后继续把结果记作旧候选。
