## 为什么是局部重做

应保留的主体有明确源码与 Host 合同证据：

1. policy 的 OFF/forced-OFF 优先级与实际模型类别边界；
2. 每次从 canonical Full block table 和当前 mapping 派生 read view；
3. `H=E+future_offset`、`S=floor(max(H-W,0)/B)*B`、`V=E-S`；
4. Draft read 与 Full slots/positions/Target metadata 的职责分离；
5. DFlash、DSpark、Eagle3 的实际 builder 接入和 Eagle proposal anchor；
6. owner pool、unknown-completion quarantine、按 completion 延长 read/derived-state 生命周期；
7. 多 gid/backend inventory 和明确 unsupported 拒绝；
8. b013719 后已确认的 DSpark、Eagle 与 legacy CP 修复。

需要 targeted rework 的部分也很集中：

- A01：为 GQA/MLA/DSA/SFA 的实际消费者建立 device exact + host capacity 的显式契约，消除 Window 新增的通用 D2H，不能用 upper 代 exact；
- 完整 engine Async：以真实 reader/HCCL stream 和 partial-submit 证明 completion happens-before，而非只靠引用计数或 mock event；
- legacy DSA-CP：固定 base/candidate 的 MRV2 guard 是真实能力缺口，需独立设计决策，不能删 guard或用 PCP 冒充；
- required backend/multi-group/FlashComm/SP/prefix/chunk/mixed 的实际模型与 A3 证据。

这些问题严重到阻止正式架构通过，但没有证据表明 policy/math/read isolation/方法主体必须推翻。新会话或 `BLOCKED` 标签本身不是重写理由。

## 推荐首个服务器问题

先处理 `A01-GQA-CURRENT-EXACT`：以当前 GLM/DSpark 实际 GQA 路线为第一条 required route，确认固定 torch_npu/CANN 的 FIA/builder 长度 ABI，再把 Window planning/projection 与 builder consumer 改成明确的 device exact + host capacity 契约，确保当前 rejection 后 exact 不回传 CPU。不要先做泛化框架。

完成条件：

- 源码扫描列清本次 route 所有 device→host 同步、CPU list/动态 chunk consumer；
- 设备端 length/projection 与独立数学 reference 在 block 边界、K/K+1、rejection、padding 下相同；
- Window ON 不新增 exact D2H，OFF 不创建 Window runtime/view；
- Full block table/slots/positions/Target 不变；
- 单 NPU native probe 与短 trace 证明实际 ABI、拷贝次数和 CPU stall；
- 形成新候选提交和新 SHA，再绑定后续实验，不能在旧冻结 SHA 上热改后继续计时。

代码设计可以先在无设备环境开始；固定 ABI schema、native 最小调用、数值和 trace 需要 A3。若固定 native ABI不能接收 device exact，保存 schema/调用失败证据，再提出最小接口方案，不能把同步移位或用 upper 填充。
