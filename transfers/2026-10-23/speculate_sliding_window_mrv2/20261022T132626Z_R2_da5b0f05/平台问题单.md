## 问题 1：正常多代的版本选择与最后 consumer（CANN/torch_npu 维护者）

API：aclmdlRIExecuteAsync、aclmdlRICaptureTaskUpdateBegin/End、ExternalEvent wait/reset/record。
项目实际顺序：本代 current 流 materialize/bind → update_stream.wait_stream(current) → current replay → update 流 UPDATE/event record → 下一代 current 写入。wait_stream 位于本代 replay 之前，不能为观测而移动。

已有依据：9.1 指南明确展示先 replay、再 UPDATE、event record；故这一先后本身不是缺陷。Runtime Model::GetStreamToAsyncExecute 的 Stars 非 AICPU 分支在执行流上提交 endGraphNotify_ 的 NtyWait；这是实质的流内完成依赖，不是 Host drain。CaptureModel::ExecuteCommon 还设置执行前后 notify。

待区分：H1，实际安装构建及本 MRV2 Graph 走该分支，完成 notify 覆盖 FIA 等全部内部消费者，下一代 current 写依赖因此完整；H2，存在未纳入该 notify 的消费者或实际走其他分支。
需要：确认本硬件/构建分支与最后消费者覆盖范围；说明重复 task-group UPDATE 与 ExternalEvent reset 的版本选择规则。源码链已收窄问题，不再笼统要求“更多 API 证据”。

现有 C15 串行 LIFE、完整连续数值/ABA 与正常 C8 NORMAL_ORDER 只支持各自范围；不能由 Host return、retire、压力无报错决定正常无额外观测的普遍安全性。
阻塞：NORMAL_UPDATE_GENERATION、NORMAL_BACKING_REUSE 的完整验收。可继续数值、Target、LIFE、异常隔离及 profiling。
