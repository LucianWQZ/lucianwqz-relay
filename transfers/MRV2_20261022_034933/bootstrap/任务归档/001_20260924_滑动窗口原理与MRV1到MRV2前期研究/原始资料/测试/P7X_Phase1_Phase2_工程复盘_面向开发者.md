## 1. Phase 1 回答什么问题

**一句话**：*「我把这个 perf commit 合进来，端到端是变快还是变慢？」*

- 设计：**A/B/A/B**（parent → perf → parent → perf），四段独立起服、独立 MRV2 取证；
- **两臂都开 W1024** —— 窗长被固定成常数，唯一变量是 **commit**；
- 长度：16K 与 128K；
- 产出：parent 池化 vs perf 池化的吞吐 / TPOT / TTFT / E2E / acceptance。

**答案**：`NO_MEASURABLE_DIFFERENCE`（16K +5.00%、128K −3.51%，两条 observed range 都重叠）。

Phase 1 检测的是**热路径改动的真实加速/减速**，量级通常是个位数百分点。

## 2. Phase 2 回答什么问题

**一句话**：*「Draft Sliding Window 这个特征，到底在什么输入长度上开始划算？」*

- 设计：**OFF vs W1024**，两者**都是 perf 树**（`1b7215c3`）—— commit 被固定成常数，

Phase 2 检测的是**特征开关的效应**，量级可以是几十到几百百分点。

## 3. 为什么两者不能混

这两件事是**正交**的，混起来会得出错误的因果结论：

| | Phase 1 | Phase 2 |
|---|---|---|
| 自变量 | **commit**（parent vs perf） | **window**（OFF vs W1024） |
| 控制变量 | window 固定为 W1024 | commit 固定为 perf |
| 期望效应量 | 个位数 % | 数十 ~ 数百 % |
| 判据 | range overlap + 2% 阈值 | 增益方向 / break-even |
| 结论 | `NO_MEASURABLE_DIFFERENCE` | `FEATURE_EFFECTIVE_AT_LONG_CONTEXT` |

**混起来的典型错误**：

- 看到 Phase 2 的 128K **+74.18%**，就以为「perf commit 带来了 +74%」——  
  错。这 +74% 是 **window 特征**带来的，两臂都是同一棵 perf 树，commit 的贡献**不在这条曲线里**。
- 看到 Phase 1 的 128K **−3.51%**，就以为「window 有害」——  
  错。Phase 1 两臂**都开了窗**，这条曲线根本没测 OFF。

> **一句话记法**：Phase 1 是「**换代码**」的效果；Phase 2 是「**开特征**」的效果。  
> 两条曲线各自只回答自己那一半，**不可互相引用**。

## 4. Performance commit 是否值得保留？

**结论：当前证据不足以判定，建议「暂留，补测后再决」。**

- ✅ **没有证据表明它是回归**：128K 的 −3.51% 落在噪声内，两条 range 重叠；
- ✅ **没有证据表明它是收益**：16K 的 +5.00% 同样被两个快 repeat 拉动，不可分离；
- ⚠️ **本机噪声太大**：perf 池化 CV 在 16K 是 0.069（parent 0.034），  
  block-to-block spread 16K 达 **19.72%**（parent 12.20%）—— 效应量被噪声淹没。

**为什么噪声这么大（可查的工程原因）**：

1. **每 cell 只有 4 个请求、并发 1**（团队原矩阵是 `conc=16 / data_num=64`）；
2. 这是**共享节点**，`load average ≈ 28–30`，其他租户随时占卡（`00_preflight/preflight.txt`）；
3. 128K cell 单次跑几十秒到两分钟（E2E ≈ 75–130 s），长窗口里机器状态漂移大。

**要做决断，缺的是「统计功效」，不是「新代码」**：  
把每 cell 的 repeats 从 3 提到 6–8，或把请求数从 4 提到 16+，让 spread 收窄到效应量以下。

## 5. Sliding Window 特征是否有效？

**结论：有效，且效果随上下文长度单调放大。**

| input | OFF acc | W1024 acc | 吞吐增益 |
|---|---|---|---|
| 16K | 6.3528 | 6.0529 | −6.96% |
| 32K | 5.6247 | 6.4062 | +12.96% |
| 64K | 3.4699 | 6.3555 | +52.67% |
| 128K | **1.7762** | **6.3831** | **+74.18%** |

- W1024 的 acceptance 在**所有长度上都稳定在 6.05–6.41**（近似水平线）；
- OFF 的 acceptance 随长度**单调坍塌**（6.35 → 1.78）；
- 两者之差就是特征的净价值 ⇒ 越长越值钱。

**这不是「优化」，这是「修复坍塌」**：OFF 在 128K 已经不是「慢一点」，  
而是投机解码**基本失效**（pos1 只有 0.46，后面的位置几乎全 0）。

## 6. 16K 为什么仍可能负收益？

16K 是唯一负收益点（**−6.96%**）。三个**叠加**的原因：

1. **没有收益空间可拿**：16K 下 OFF 的 acceptance 已经 **6.3528**，  
   而 W1024 是 6.0529 —— 开窗后**反而略低**（−4.72%）。  
   一个已经很健康的长上下文，滑窗拿不到它该拿的东西，却要付它的成本。
2. **固定开销占比最大**：滑窗路径的裁剪 / 投影 / 掩码构造是**每次 decode step 的固定成本**。  
   16K 时 decode 步数最多（E2E 最短、TPOT 最低），单位成本被摊得最薄 → 开销最容易吃掉收益。
3. **采样噪声与效应量同量级**：OFF 16K 的 CV = 0.056、W1024 CV = 0.035；  
   加上并发 1 / 4 请求，−6.96% 里有多少是真信号、多少是噪声，**本轮无法分离**。

> 注意：**首轮 smoke 16K 是 −0.83%**，历史 MRV1 是 **+10.2%** —— 三轮方向都不一致。  
> 所以「16K 负收益」应读作**「16K 无收益 / 略负」**，而不是一个稳定的负号。

## 7. 32K 的 break-even

- 16K：**−6.96%**（在线下）
- 32K：**+12.96%**（已过线）

⇒ **break-even 落在 16K 与 32K 之间**，本轮没有落点在阈值上，只能夹逼。  
要精确定位，需要补测 **24K**（或 20K / 28K）这一档。

**为什么在 32K 过线**：OFF 的 acceptance 从 16K 的 6.35 掉到 32K 的 5.62  
（−11.5%）——坍塌已经开始，滑窗的「救援」价值首次超过它的固定开销。  
换句话说：**break-even 的本质是「OFF 的坍塌速度」追上「滑窗的开销」的那个长度**。

## 8. 64K / 128K 为什么收益快速变大？

因为 OFF 在这里**不再是「慢」，而是「坏掉了」**：

| input | OFF pos1 | OFF pos8 | OFF acc |
|---|---|---|---|
| 16K | 0.9028 | 0.4259 | 6.3528 |
| 32K | 0.8834 | 0.2680 | 5.6247 |
| 64K | 0.8159 | 0.0202 | 3.4699 |
| 128K | **0.4607** | **0.0006** | **1.7762** |

- 64K：pos8 已掉到 **0.02** → 只有前 3 个位置还在贡献，acc 掉到 3.47；
- 128K：**连 pos1 都只有 0.46** → 整个草稿序列基本被拒，acc 塌到 1.78  
  （理论上「不接受任何 token」的下限是 1.0，1.78 已经贴近地板）。

而 W1024 在所有长度上都把 pos1 稳在 **0.90–0.93**、pos8 稳在 **0.42–0.48**。  
所以**收益 = OFF 的坍塌深度**，坍塌越深，增益越大 ⇒ 128K 的 +74.18% 不是「优化得好」，  
而是「修复了一个本来要失效的路径」。

## 9. Acceptance collapse 机制

从 per-position 数据可以读出一条清晰的因果链：

```text
输入长度 ↑
  → 草稿模型要看的 KV 历史变长
  → 关窗时，draft 注意力被"淹没"在无关远端上下文里（或 draft 训练分布外）
  → 草稿提出的 token 被主模型逐步拒绝
  → 拒绝沿位置向后传导：pos1 ↓ 拖累 pos2 ↓ …
  → mean acceptance length 坍塌 → 每个 decode step 只吐 ~1.8 个 token
  → TPOT 暴涨（128K：11.8 ms → 39.5 ms）、吞吐崩塌（26.8 → 15.4 tok/s）
```

**关键观测**：坍塌是**沿位置向后传导的**，不是一次性全体失效 ——  
128K 的 pos1 还有 0.46，pos2 就只剩 0.19。这说明**问题出在 draft 的注意力视野**，  
而不是 draft 的权重本身（否则 pos1 会一起崩）。

滑窗把它截断为「只看最近 1024 个 token」⇒ 草稿重新落在训练时见过的短上下文分布里  
⇒ pos1 回到 0.93，整条链恢复。

### 10.2 精确定位 break-even

- 补测 **24K**（必要时 20K / 28K），把 break-even 从「16K–32K 之间」收敛到一个点。

### 10.3 解释 pos1 在 128K 掉到 0.46 的根因

- 这是整个特征的**核心证据**，值得单独追：
  - draft 的注意力是否在做**全历史 softmax**（无掩码）？
  - draft 是否依赖某个**位置编码外推**行为（128K 超出 training 长度）？
  - OFF 下 draft 接收的 KV 里，远端 block 的贡献占比是多少？
- 手段：在 draft speculator 里开 **per-position attention entropy / 远端 token 权重占比**的观测，  
  与 per-position acceptance 逐位置对齐。

### 10.4 确认「开销是否随窗长变化」

- 目前只测了 W1024。若要谈「开多大窗最划算」，至少要 **512 / 2048 / 4096** 各点一测，  
  画 **acceptance vs 窗长** 与 **step time vs 窗长** 两条线，  
  其交点才是真正的最优窗长。

### 10.5 不要做的
